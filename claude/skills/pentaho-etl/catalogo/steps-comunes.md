# Most-used steps in PDI 9.4 — annotated guide for writing `.ktr` by hand

Guide to the ~45 steps that show up in a typical ETL for a Big Data course. It complements `INDICE.md`
(full list with ids) and `steps/<id>.xml` (default XML generated by the installation itself).
The general `.ktr` format (`<info>` header, `<connection>`, `<order>`/hops, `<notepads>`…) is in `manual/`.

**How the examples are built.** Each XML block shows **only the step's own fragment**, i.e.
what goes inside `<step>` *after* the common wrapper. A complete step is:

```xml
<step>
  <name>Leer ventas</name>            <!-- unique within the transformation; hops reference it -->
  <type>CsvInput</type>               <!-- plugin ID, see INDICE.md -->
  <description/>
  <distribute>Y</distribute>
  <custom_distribution/>
  <copies>1</copies>
  <partitioning><method>none</method><schema_name/></partitioning>
  <!-- ======= STEP-SPECIFIC FRAGMENT (what the examples below show) ======= -->
  <attributes/>
  <cluster_schema/>
  <remotesteps><input></input><output></output></remotesteps>
  <GUI><xloc>100</xloc><yloc>100</yloc><draw>Y</draw></GUI>
</step>
```

Source of each example: `samples/...` is given when it comes from the installation's samples
(`data-integration/samples/`), or *default* when it comes from `steps/<id>.xml` / from filling in the meta via the API.
Every tag in this guide was verified against the samples or against the real `getXML()` of 9.4
(see «Verification» at the end). Some parts were shortened (`...`) for readability.

## Rules that apply to all steps

1. **`<type>` = plugin id**, case-sensitive (`CsvInput`, not `CSV file input` or `csvinput`).
2. **Start from the default XML** (`steps/<id>.xml`) and change what you need. On load, each step reads its
   tags with `XMLHandler.getTagValue`; a missing tag almost always becomes `null` → default value, but not
   in every case (some steps throw an NPE or end up in a weird state). Copying the complete block is the safe option.
3. **Field types** (`<type>` inside `<field>`): `String`, `Integer`, `Number`, `BigNumber`, `Date`,
   `Timestamp`, `Boolean`, `Binary`, `Internet Address`, `Serializable`, `None`. `<length>`/`<precision>` `-1` = undefined.
   Formats: date `yyyy-MM-dd`, `dd/MM/yyyy HH:mm:ss`; number `#,##0.00`, `#.#`, `0`.
4. **Watch out: a single `<field>` can contain a `<name>` and a `<type>`** that have nothing to do with the
   step's `<name>`/`<type>`. If you process the XML with regex, anchor by depth; better yet, use a DOM parser.
5. **Steps that name other steps** (lookup, merge, filters, switch, append…) need **both things**:
   the other step's name in their tag **and** the corresponding hop in `<order>`. If the name in the tag does not
   exactly match an existing `<name>`, Kettle silently ignores it (or fails on verification).
   | Step | Tag(s) that name steps | Stream type |
   |---|---|---|
   | `StreamLookup` | `<from>` | *info* (the lookup step) |
   | `MergeJoin` | `<step1>`, `<step2>` | *info* ×2 |
   | `MergeRows` | `<reference>`, `<compare>` | *info* ×2 |
   | `JoinRows` | `<main>` (optional) | main input |
   | `Append` | `<head_name>`, `<tail_name>` | *info* ×2 |
   | `FilterRows` | `<send_true_to>`, `<send_false_to>` | *targets* |
   | `SwitchCase` | `<target_step>` of each `<case>`, `<default_target_step>` | *targets* |
   | `TableInput` | `<lookup>` (the step that feeds the `?`) | *info* |
6. **XML escapes.** Spoon writes `=` as `&#x3d;`, `<` as `&#x3c;`, `>` as `&gt;`. When writing by hand it is enough to
   escape `<` and `&` (`&lt;`, `&amp;`); `=` and `>` can be left as is.
7. **Paths.** Use `${Internal.Entry.Current.Directory}` or `${Internal.Transformation.Filename.Directory}` for
   paths relative to the `.ktr` (the samples use the latter). Forward slashes `/` also work on Windows.
8. **Connections.** `<connection>NOMBRE</connection>` inside a step references a
   `<connection><name>NOMBRE</name>...` block at the `<transformation>` level (see `manual/`). The names must match.
9. **Hops**: `<order><hop><from>A</from><to>B</to><enabled>Y</enabled></hop>...</order>`.

## Input

### CSV file input — `CsvInput`
Reads a CSV/delimited file quickly (a single file, NIO). The most used step for loading datasets.
Example: `samples/transformations/Closure generator - standard mondrian sample.ktr`
```xml
<filename>${Internal.Transformation.Filename.Directory}/files/closure_input.txt</filename>
<filename_field/>
<rownum_field/>
<include_filename>N</include_filename>
<separator>;</separator>
<enclosure>"</enclosure>
<header>Y</header>
<buffer_size>50000</buffer_size>
<lazy_conversion>N</lazy_conversion>
<add_filename_result>N</add_filename_result>
<parallel>N</parallel>
<newline_possible>Y</newline_possible>
<encoding>UTF-8</encoding>
<fields>
  <field>
    <name>supervisor_id</name>
    <type>Integer</type>
    <format/>
    <currency/><decimal/><group/>
    <length>-1</length>
    <precision>-1</precision>
    <trim_type>none</trim_type>
  </field>
  <field>
    <name>name</name>
    <type>String</type>
    <format/><currency/><decimal/><group/>
    <length>-1</length><precision>-1</precision>
    <trim_type>both</trim_type>
  </field>
</fields>
```
**Pitfalls.** The `<field>` elements are mapped **by position**, not by header name: their order must be the order
of the file's columns (the name can be anything). `<header>Y</header>` only skips the first line.
`<lazy_conversion>Y</lazy_conversion>` leaves the values as unconverted bytes (fast, but afterwards
Calculator/JS/lookups may fail or compare incorrectly: leave it at `N` unless you know what you are doing).
Tab separator: the literal TAB character, written `<separator>&#x9;</separator>` (in Spoon, the «Insert TAB» button).
Dates: `<type>Date</type>` + `<format>yyyy-MM-dd</format>`; if the format does not match, the step aborts.
Comma decimals: `<decimal>,</decimal><group>.</group>`. It does not support wildcards or multiple files → `TextFileInput`.

### Text file input — `TextFileInput`
General-purpose reader: multiple files, wildcards (regex), fixed width, compressed files, filters, error handling.
Example: `samples/transformations/Getting Started Transformation.ktr` (shortened)
```xml
<accept_filenames>N</accept_filenames>
<separator>,</separator>
<enclosure>"</enclosure>
<header>Y</header>
<nr_headerlines>1</nr_headerlines>
<footer>N</footer>
<noempty>Y</noempty>
<format>mixed</format>             <!-- DOS | Unix | mixed -->
<encoding/>
<file>
  <name>${Internal.Transformation.Filename.Directory}/files/Zipssortedbycitystate.csv</name>
  <filemask/>                       <!-- Java regex, e.g. ventas_.*\.csv (with <name> = folder) -->
  <exclude_filemask/>
  <file_required>N</file_required>
  <include_subfolders>N</include_subfolders>
  <type>CSV</type>                  <!-- CSV | Fixed -->
  <compression>None</compression>
</file>
<filters></filters>
<fields>
  <field>
    <name>CITY</name>
    <type>String</type>
    <format/><currency>$</currency><decimal>.</decimal><group>,</group>
    <nullif>-</nullif>
    <ifnull/>
    <position>-1</position>
    <length>25</length>
    <precision>-1</precision>
    <trim_type>none</trim_type>
    <repeat>N</repeat>
  </field>
</fields>
<limit>0</limit>
<error_ignored>N</error_ignored>
...
```
**Pitfalls.** The file type goes **inside** `<file>` (`<type>CSV</type>`), not at step level. If several files
are given, `<file>` carries several `<name>`/`<filemask>`… in parallel (same order). `<filemask>` is a **regex**,
not a glob (`.*\.csv`, not `*.csv`). It has a great many tags (85 lines by default): copy `steps/TextFileInput.xml`.

### Microsoft Excel input — `ExcelInput`
Reads sheets from `.xls`, `.xlsx` or `.ods`.
Example: `samples/transformations/XML Join - Create a multilayer XML file.ktr` (shortened)
```xml
<header>Y</header>
<noempty>Y</noempty>
<stoponempty>N</stoponempty>
<limit>0</limit>
<encoding/>
<add_to_result_filenames>Y</add_to_result_filenames>
<accept_filenames>N</accept_filenames>
<file>
  <name>${Internal.Transformation.Filename.Directory}/files/datos.xlsx</name>
  <filemask/>
  <exclude_filemask/>
  <file_required>N</file_required>
  <include_subfolders>N</include_subfolders>
</file>
<fields>
  <field>
    <name>orderNumber</name>
    <type>Integer</type>
    <length>-1</length>
    <precision>-1</precision>
    <trim_type>none</trim_type>
    <repeat>N</repeat>
    <format/><currency/><decimal/><group/>
  </field>
</fields>
<sheets>
  <sheet>
    <name>Hoja1</name>
    <startrow>0</startrow>
    <startcol>0</startcol>
  </sheet>
</sheets>
<strict_types>N</strict_types>
<error_ignored>N</error_ignored>
...
<spreadsheet_type>POI</spreadsheet_type>
```
**Pitfalls.** `<spreadsheet_type>`: `JXL` (the **default**, old `.xls` only), `POI` (`.xls` and `.xlsx`),
`SAX_POI` (large `.xlsx`, streaming), `ODS`. **For `.xlsx` you must set `POI` or `SAX_POI`**; with JXL it fails.
Without `<sheets>` it reads all sheets. `<startrow>`/`<startcol>` start at 0. Fields are mapped by position
starting from `startcol`; with `<header>Y</header>` the first row is the header.

### Table input — `TableInput`
Runs a `SELECT` against a connection and emits the rows.
Example: `samples/jobs/process all tables/Process one table.ktr`
```xml
<connection>SampleDataAdmin.H2</connection>
<sql>SELECT count(*) as NrRows FROM ${TABLENAME}</sql>
<limit>0</limit>
<lookup/>                              <!-- step that feeds the ? in the SQL (info stream) -->
<execute_each_row>N</execute_each_row>
<variables_active>Y</variables_active> <!-- substitute ${VAR} in the SQL -->
<lazy_conversion_active>N</lazy_conversion_active>
```
**Pitfalls.** Without `<variables_active>Y</variables_active>` the `${...}` are sent literally to the DB. With
`?` parameters: put the provider step in `<lookup>` + a hop, and `<execute_each_row>Y</execute_each_row>` if it has
to run once per row. Escape `<` in the SQL (`&lt;`). It has no `<fields>`: the structure comes from the DB.

### Generate rows — `RowGenerator`
Generates N rows with constant fields (useful for triggering a flow or for tests). The most used step in the samples (196).
Example: `samples/transformations/Value Mapper - Same and new field.ktr`
```xml
<fields>
  <field>
    <name>A</name>
    <type>String</type>
    <format/>
    <currency/><decimal/><group/>
    <nullif>Five</nullif>          <!-- the field's VALUE goes in <nullif>! -->
    <length>-1</length>
    <precision>-1</precision>
    <set_empty_string>N</set_empty_string>
  </field>
</fields>
<limit>1</limit>
<never_ending>N</never_ending>
<interval_in_ms/>
<row_time_field/>
<last_time_field/>
```
**Classic pitfall.** The constant value is stored in **`<nullif>`** (historical name). Same in `Constant`; not in
`DataGrid` (it uses `<data>`). For an empty string: `<set_empty_string>Y</set_empty_string>`.
`<limit>` accepts variables (`${N}`).

### Data grid — `DataGrid`
Fixed data table written inside the step itself (small dimensions, mappings, tests).
Example: `samples/transformations/Rules Accumulator - Solve Golfer Rule.ktr`
```xml
<fields>
  <field>
    <name>position</name>
    <type>Integer</type>
    <format/><currency/><decimal/><group/>
    <length>-1</length>
    <precision>-1</precision>
    <set_empty_string>N</set_empty_string>
  </field>
</fields>
<data>
  <line><item>1</item></line>
  <line><item>2</item></line>
</data>
```
**Pitfalls.** Each `<line>` carries one `<item>` per field, **in the same order** as `<fields>`. Values are
parsed with the field's `<format>` (dates: set `<format>yyyy-MM-dd</format>`).

### JSON input — `JsonInput`
Extracts fields from JSON with JSONPath, from a file or from a stream field.
Example (from a field): `samples/transformations/JsonInput - read incoming stream.ktr` (shortened)
```xml
<include>N</include>
<include_field/>
<rownum>N</rownum>
<addresultfile>N</addresultfile>
<readurl>N</readurl>
<removeSourceField>N</removeSourceField>
<IsIgnoreEmptyFile>N</IsIgnoreEmptyFile>
<doNotFailIfNoFile>N</doNotFailIfNoFile>
<ignoreMissingPath>N</ignoreMissingPath>
<rownum_field/>
<file>
  <name/>                           <!-- read from a file: path here and <IsInFields>N -->
  <filemask/>
  <exclude_filemask/>
  <file_required>N</file_required>
  <include_subfolders>N</include_subfolders>
</file>
<fields>
  <field>
    <name>title</name>
    <path>$..title</path>
    <type>String</type>
    <format/><currency/><decimal/><group/>
    <length>-1</length><precision>-1</precision>
    <trim_type>none</trim_type>
    <repeat>N</repeat>
  </field>
</fields>
<limit>0</limit>
<IsInFields>Y</IsInFields>          <!-- Y = the JSON comes in the <valueField> field -->
<IsAFile>N</IsAFile>                <!-- Y = <valueField> contains a file PATH -->
<valueField>Content</valueField>
...
```
**Pitfalls.** All the paths in the same step must return the **same number of elements** (they are combined by
index); otherwise, a «data structure mismatch» error or misaligned rows. `$..x` (deep scan) returns every `x`
at any level. For keys that may be missing: `<ignoreMissingPath>Y</ignoreMissingPath>`.

### Get system info — `SystemInfo`
Adds system dates, arguments, transformation name, hostname…
Example: `samples/transformations/Get System Info - Command Line Argument and filter.ktr`
```xml
<fields>
  <field>
    <name>hoy</name>
    <type>system date (variable)</type>
  </field>
  <field>
    <name>arg1</name>
    <type>command line argument 1</type>
  </field>
</fields>
```
**Pitfalls.** `<type>` here is **not a data type** but the code of the system datum, in English and with
spaces: `system date (variable)`, `system date (fixed)`, `today start`, `yesterday start`,
`last month start`, `Hostname`, `IP address`, `Current PID`, `command line argument 1`… (values seen in the samples).
If it has no incoming hop it generates **one** row; if it has one, it adds the fields to every row.

### Get variables — `GetVariable`
Turns variables/parameters (`${VAR}`) into fields.
Example: `samples/transformations/GetXMLData - Differents Options.ktr`
```xml
<fields>
  <field>
    <name>filename</name>
    <variable>${Internal.Transformation.Filename.Directory}/files/test_xml_file.xml</variable>
    <type>String</type>
    <format/><currency/><decimal/><group/>
    <length>-1</length><precision>-1</precision>
    <trim_type>none</trim_type>
  </field>
</fields>
```
**Pitfall.** `<variable>` holds the expression **with** `${}` (text can be concatenated). Same as `SystemInfo`:
with no input it generates one row.

### Table output — `TableOutput`
Bulk INSERT into a table.
Example: `samples/transformations/Getting Started Transformation.ktr`
```xml
<connection>SampleDataAdmin.H2</connection>
<schema/>
<table>SALES_DATA</table>
<commit>1000</commit>
<truncate>Y</truncate>               <!-- TRUNCATE before inserting -->
<ignore_errors>N</ignore_errors>
<use_batch>Y</use_batch>
<specify_fields>N</specify_fields>
<partitioning_enabled>N</partitioning_enabled>
<partitioning_field/>
<partitioning_daily>N</partitioning_daily>
<partitioning_monthly>Y</partitioning_monthly>
<tablename_in_field>N</tablename_in_field>
<tablename_field/>
<tablename_in_table>Y</tablename_in_table>
<return_keys>N</return_keys>
<return_field/>
<fields>
</fields>
```
With explicit mapping (`<specify_fields>Y</specify_fields>`):
```xml
<fields>
  <field><column_name>CUSTOMER_ID</column_name><stream_name>id</stream_name></field>
</fields>
```
**Pitfalls.** With `<specify_fields>N</specify_fields>` the **stream names must match** the columns
(and there can be no extra fields). The table **must exist** (Spoon generates the CREATE SQL with the «SQL» button;
in an automated ETL use `ExecSQL` beforehand or the `SQL` job entry). It only inserts: for an upsert, `InsertUpdate`.

### Insert / update — `InsertUpdate`
Upsert: looks up by key; if the row does not exist it inserts it, if it exists it updates the flagged fields.
Example: `samples/transformations/User Defined Java Class - Real-time search on Twitter.ktr`
```xml
<connection>Sampledata</connection>
<commit>100</commit>
<update_bypassed>N</update_bypassed>   <!-- Y = insert only, never update -->
<lookup>
  <schema/>
  <table>pentaho_tweets</table>
  <key>
    <name>id</name>                    <!-- stream field -->
    <field>id</field>                  <!-- table column -->
    <condition>=</condition>
    <name2/>                           <!-- 2nd field for BETWEEN -->
  </key>
  <value>
    <name>id</name>                    <!-- table column -->
    <rename>id</rename>                <!-- stream field -->
    <update>N</update>                 <!-- N = only in the INSERT -->
  </value>
  <value>
    <name>tweet</name>
    <rename>tweet</rename>
    <update>Y</update>
  </value>
</lookup>
```
**Pitfalls.** Mind the meaning of `<name>`: in `<key>` it is the **stream field** and `<field>` the column; in
`<value>` it is the other way round (`<name>` = column, `<rename>` = stream field). The key columns must also be
in `<value>` (with `<update>N</update>`) so that they get inserted. It is slow (one query per row): without an index
on the key, it crawls.

### Update — `Update`
UPDATE by key only (does not insert).
Example: `samples/jobs/changelog-groups/process per group.ktr`
```xml
<connection>SampleDataAdmin.H2</connection>
<skip_lookup>N</skip_lookup>
<commit>100</commit>
<use_batch>N</use_batch>
<error_ignored>N</error_ignored>      <!-- Y = do not fail if the key does not exist -->
<ignore_flag_field/>
<lookup>
  <schema/>
  <table>CHANGELOG</table>
  <key><name>ID</name><field>ID</field><condition>=</condition><name2/></key>
  <value><name>FOO</name><rename>FOO</rename></value>
</lookup>
```
**Pitfall.** By default it **fails** if it does not find the row (`<error_ignored>N</error_ignored>`). `<value>` has
no `<update>` (all of them are updated).

### JSON output — `JsonOutput`
Generates JSON (to a file, to a field, or both).
Example: `samples/transformations/Servlet Data Example.ktr` (shortened)
```xml
<outputValue>outputValue</outputValue>  <!-- name of the output field if operation_type uses it -->
<jsonBloc>data</jsonBloc>               <!-- name of the root array: {"data":[...]} -->

<operation_type>both</operation_type>   <!-- writetofile | outputvalue | both -->
<compatibility_mode>N</compatibility_mode>
<encoding>UTF-8</encoding>
<addtoresult>N</addtoresult>
<file>
  <name>${Internal.Transformation.Filename.Directory}/output/datos</name>
  <extention>json</extention>
```

for a single array. `<element>` is the key in the JSON; `<name>` is the stream field.

### Write to log — `WriteToLog`

```xml
<loglevel>log_level_basic</loglevel>   <!-- log_level_nothing|error|minimal|basic|detailed|debug|rowlevel -->
<displayHeader>N</displayHeader>
<logmessage>Fila retrasada</logmessage>
<fields>
  <field><name>counter</name></field>

```
**Pitfall.** If the step's level is more detailed than the run's (e.g. `log_level_detailed` and Pan with
`-level=Basic`) nothing shows up. With an empty `<fields>` it logs all fields.

## Transform

### Add constants — `Constant`
Adds fields with a fixed value.
Example: `samples/transformations/XML Input Stream (StAX) Test 2 - Element Blocks.ktr`
```xml
<fields>
  <field>
    <name>item_type</name>
    <type>String</type>
    <format/><currency/><decimal/><group/>
    <nullif>del</nullif>               <!-- the VALUE goes in <nullif>, as in RowGenerator -->
    <length>-1</length>
    <precision>-1</precision>
    <set_empty_string>N</set_empty_string>
  </field>
</fields>
```
**Pitfall.** It does not substitute variables: `${VAR}` stays literal → use `GetVariable`.

### Add sequence — `Sequence`
Adds a counter (or a database sequence).
Example: `samples/transformations/transformation-executor/trans-executor-parent.ktr`
```xml
<valuename>test_id</valuename>
<use_database>N</use_database>
<connection/>
<schema/>
<seqname>SEQ_</seqname>
<use_counter>Y</use_counter>
<counter_name/>
<start_at>1</start_at>
<increment_by>1</increment_by>
<max_value>999999999</max_value>
```
**Pitfall.** With several copies of the step (`<copies>` > 1) each copy counts on its own (repeated ids) unless they
share a `<counter_name>`. The value is `Integer`.

### Calculator — `Calculator`
Predefined calculations on up to 3 fields (A, B, C): arithmetic, dates, strings, hashes.
Example: `samples/transformations/Rounding.ktr`
```xml
<calculation>
  <field_name>precio_iva</field_name>
  <calc_type>MULTIPLY</calc_type>
  <field_a>precio</field_a>
  <field_b>factor_iva</field_b>
  <field_c/>
  <value_type>Number</value_type>
  <value_length>-1</value_length>
  <value_precision>2</value_precision>
  <remove>N</remove>                  <!-- Y = temporary field, not output by the step -->
  <conversion_mask/>
  <decimal_symbol/>
  <grouping_symbol/>
  <currency_symbol/>
</calculation>
<calculation>
  <field_name>anio</field_name>
  <calc_type>YEAR_OF_DATE</calc_type>
  <field_a>fecha</field_a>
  <field_b/><field_c/>
  <value_type>Integer</value_type>
  <value_length>-1</value_length>
  <value_precision>-1</value_precision>
  <remove>N</remove>
  <conversion_mask/>
</calculation>
```
Each calculation is a `<calculation>` **directly** inside the fragment (there is no wrapping `<fields>`).
Useful `<calc_type>` codes (verified in `CalculatorMetaFunction`): `CONSTANT`, `COPY_FIELD`, `ADD`,
`SUBTRACT`, `MULTIPLY`, `DIVIDE`, `SQUARE`, `SQUARE_ROOT`, `PERCENT_1` (A/B*100), `PERCENT_2` (A-A*B/100),
`PERCENT_3` (A+A*B/100), `ADD3`, `ABS`, `CEIL`, `FLOOR`, `ROUND_1`, `ROUND_2` (A with B decimals),
`ROUND_STD_1`, `ROUND_STD_2`, `REMAINDER`, `NVL` (A if not null, otherwise B), `ADD_DAYS`, `ADD_MONTHS`,
`ADD_HOURS`, `DATE_DIFF` (days B-A), `YEAR_OF_DATE`, `MONTH_OF_DATE`, `DAY_OF_MONTH`, `DAY_OF_WEEK`,
`DAY_OF_YEAR`, `WEEK_OF_YEAR`, `QUARTER_OF_DATE`, `REMOVE_TIME_FROM_DATE`, `UPPER_CASE`, `LOWER_CASE`,
`INIT_CAP`, `STRING_LEN`, `GET_ONLY_DIGITS`, `REMOVE_DIGITS`, `MD5`, `SHA1`, `CRC32`, `LEVENSHTEIN_DISTANCE`.
**Pitfalls.** A calculation can use the result of an earlier one in the same step (order matters). The types of A
and B must be compatible (`DIVIDE` of two Integers gives an Integer: truncated → set `<value_type>Number</value_type>`).
`CONSTANT` takes its value from `<field_a>`. For free-form expressions: `Formula` or `Janino`.

### Formula — `Formula`
Spreadsheet-style expressions (LibFormula / OpenFormula).
Structure (default + `FormulaMetaFunction`; there are no samples):
```xml
<formula>
  <field_name>margen</field_name>
  <formula_string>IF([ventas] = 0; 0; ([ventas] - [coste]) / [ventas])</formula_string>
  <value_type>Number</value_type>
  <value_length>-1</value_length>
  <value_precision>-1</value_precision>
  <replace_field/>                     <!-- name of an existing field to overwrite -->
</formula>
```
**Pitfalls.** Fields go in square brackets `[field]`; the argument separator is **`;`** (not a comma); strings use
double quotes; concatenate with `&`. One `<formula>` per field, directly in the fragment. Slower than Calculator;
for Java logic use `Janino`.

### User defined Java expression — `Janino`
A compiled Java expression per field (fast, typed).
Example: `samples/transformations/XML Input Stream (StAX) Test 3 - Attribute Groups.ktr`
```xml
<formula>
  <field_name>group_element_id</field_name>
  <formula_string>(xml_data_name.equals("ID")) ? xml_element_id : xml_parent_element_id</formula_string>
  <value_type>Integer</value_type>
  <value_length>-1</value_length>
  <value_precision>-1</value_precision>
  <replace_field/>
</formula>
```
**Pitfalls.** Fields are used by name as Java variables (`String`, `Long` for Integer, `Double` for Number,
`java.util.Date`, `BigDecimal`). A Kettle Integer = `Long`: `edad + 1` yields a `long`, and `<value_type>` must match
the Java type the expression returns. Nulls: check `field == null` before using it. Compare strings with
`.equals`, not `==`. Escape `<`, `&&` → `&lt;`, `&amp;&amp;`.

### Select values — `SelectValues`
Select/rename/reorder fields (tab 1), remove fields (2), change type/format (3, «Meta-data»).
Examples: `samples/transformations/XML Input Stream (StAX) Test 2 - Element Blocks.ktr` and
`samples/transformations/Denormaliser - capturing last state timestamp.ktr`
```xml
<fields>
  <field>
    <name>xml_data_value</name>
    <rename>item_product_id</rename>
    <length>-2</length>
    <precision>-2</precision>
  </field>
  <field>
    <name>item_type</name>
  </field>
  <select_unspecified>N</select_unspecified>   <!-- Y = also keep the fields not listed -->
  <remove>
    <name>group</name>
  </remove>
  <meta>
    <name>fecha_txt</name>
    <rename>fecha</rename>
    <type>Date</type>
    <length>-2</length>
    <precision>-2</precision>
    <conversion_mask>dd/MM/yyyy</conversion_mask>
    <date_format_lenient>false</date_format_lenient>
    <date_format_locale/>
    <date_format_timezone/>
    <lenient_string_to_number>false</lenient_string_to_number>
    <encoding/>
    <decimal_symbol/>
    <grouping_symbol/>
    <currency_symbol/>
    <storage_type/>
  </meta>
</fields>
```
**Pitfalls.** `<field>`, `<select_unspecified>`, `<remove>` and `<meta>` **all go inside `<fields>`**.
If there is any `<field>`, **only those are output** (in that order) unless `<select_unspecified>Y`. `-2` = do not
change length/precision. In `<meta>`, `<name>` is the name **after** the rename from tab 1 if both were used in the
same step (better to use one step per operation). Changing `<type>` in `<meta>` converts the value
(String→Date uses `<conversion_mask>`).

### Sort rows — `SortRows`
Sorts the stream (in memory + temporary files).
Example: `samples/transformations/Analytic Query - Random Value Example.ktr`
```xml
<directory>%%java.io.tmpdir%%</directory>
<prefix>out</prefix>
<sort_size>1000000</sort_size>
<free_memory/>
<compress>N</compress>
<compress_variable/>
<unique_rows>N</unique_rows>          <!-- Y = also removes duplicates by the key -->
<fields>
  <field>
    <name>groupseq</name>
    <ascending>Y</ascending>
    <case_sensitive>N</case_sensitive>
    <collator_enabled>N</collator_enabled>
    <collator_strength>0</collator_strength>
    <presorted>N</presorted>
  </field>
</fields>
```
**Pitfalls.** It is a **blocking** step (emits nothing until it has read everything). It is a prerequisite of `MergeJoin`,
`MergeRows`, `GroupBy`, `Unique`, `Denormaliser`: you must sort **by the same keys and in the same order**.
`%%java.io.tmpdir%%` is valid system-variable syntax (do not touch it).

### Unique rows — `Unique`
Removes **consecutive** duplicates (sorted input).
Example: `samples/transformations/DistinctCount.ktr`
```xml
<count_rows>N</count_rows>
<count_field/>
<reject_duplicate_row>N</reject_duplicate_row>
<error_description/>
<fields>
  <field>
    <name>v1</name>
    <case_insensitive>N</case_insensitive>
  </field>
</fields>
```
**Pitfalls.** **Requires input sorted** by those fields (otherwise it only removes adjacent repeats). With an empty
`<fields>` it compares the whole row. Without sorting: `UniqueRowsByHashSet` (same `<fields><field><name>` schema, uses memory).

### Group by — `GroupBy`
Aggregations per group (SUM, COUNT, AVG…).
Example: `samples/transformations/Calculate median and percentiles using the group by steps.ktr` +
`samples/transformations/real-time-streaming/Twitter JSON parsing and hashtag aggregation.ktr`
```xml
<all_rows>N</all_rows>
<ignore_aggregate>N</ignore_aggregate>
<field_ignore/>
<directory>%%java.io.tmpdir%%</directory>
<prefix>grp</prefix>
<add_linenr>N</add_linenr>
<linenr_fieldname/>
<give_back_row>N</give_back_row>
<group>
  <field><name>provincia</name></field>
</group>
<fields>
  <field>
    <aggregate>total_ventas</aggregate>  <!-- name of the result field -->
    <subject>importe</subject>           <!-- field being aggregated -->
    <type>SUM</type>
    <valuefield/>                         <!-- separator for CONCAT_STRING, percentile for PERCENTILE -->
  </field>
  <field>
    <aggregate>n</aggregate>
    <subject>id</subject>
    <type>COUNT_ALL</type>
    <valuefield/>
  </field>
</fields>
```
`<type>` codes: `SUM`, `AVERAGE`, `MEDIAN`, `PERCENTILE`, `MIN`, `MAX`, `COUNT_ALL`, `COUNT_DISTINCT`, `COUNT_ANY`,
`CONCAT_COMMA`, `CONCAT_STRING`, `FIRST`, `LAST`, `FIRST_INCL_NULL`, `LAST_INCL_NULL`, `CUM_SUM`, `CUM_AVG`,
`STD_DEV`, `STD_DEV_SAMPLE`, `PERCENTILE_NEAREST_RANK`.
**Pitfalls.** **Requires input sorted by the `<group>` fields** (put a `SortRows` before it); otherwise repeated
groups come out with no error. Careful: `<type>` here is the aggregation, not the data type. `COUNT_ALL` counts rows
with a non-null value in `<subject>` (`COUNT_ANY` counts all of them). No `<group>` → a single total.

### Memory group by — `MemoryGroupBy`
Same as Group by but with an in-memory hash: **does not require sorted input**.
Example: `samples/transformations/real-time-streaming/Twitter JSON parsing and hashtag aggregation.ktr`
```xml
<give_back_row>N</give_back_row>
<group>
  <field><name>hashtag</name></field>
</group>
<fields>
  <field>
    <aggregate>count</aggregate>

  </field>

```
**Pitfalls.** Same codes as `GroupBy` except `CUM_SUM`, `CUM_AVG`, `STD_DEV_SAMPLE`, `PERCENTILE_NEAREST_RANK`.

### Value mapper — `ValueMapper`

Example: `samples/transformations/Automatic Documentation Output - Generate Kettle HTML Documenation.ktr`

```xml
<field_to_use>extension</field_to_use>
<target_field>FileType</target_field>  <!-- empty = overwrites field_to_use -->
```

### String operations — `StringOperations`
Trim, upper/lower case, padding, InitCap, removing digits/special characters, escapes.
Structure (via the API, no samples):
```xml
<fields>
```

### Replace in string — `ReplaceString`
Search/replace (literal or regex) in String fields.
Example: `samples/transformations/XML Input Stream (StAX) Test 5 - Performance Test Data for Element Blocks.ktr`

### Split fields — `FieldSplitter`
Splits a field into several by a delimiter (new columns).
Example: `samples/transformations/Row Normaliser - turn a single row into 3 rows.ktr`

### Concat fields — `ConcatFields`
Concatenates fields into a new one (shares its meta with Text file output).
Example: `samples/jobs/process all tables/Get list of tables.ktr` (shortened: the `<file>` block is not needed but must be present)
```xml
<separator>.</separator>
<enclosure>"</enclosure>
<enclosure_forced>N</enclosure_forced>

<fields>
```

## Flow

### Filter rows — `FilterRows`
Splits the stream according to a condition: true → one step, false → another.
Example: `samples/transformations/XML Input Stream (StAX) Test 2 - Element Blocks.ktr` (simple condition)
```xml
<send_true_to>Filas válidas</send_true_to>
<send_false_to>Filas descartadas</send_false_to>
<compare>
  <condition>
    <negated>N</negated>
    <leftvalue>xml_data_name</leftvalue>
    <function>=</function>
    <rightvalue/>                       <!-- name of ANOTHER field, to compare field against field -->
    <value>                             <!-- or a constant -->
      <name>constant</name>
      <type>String</type>
      <text>Value</text>
      <length>-1</length>
      <precision>-1</precision>
      <isnull>N</isnull>
      <mask/>
    </value>
  </condition>
</compare>
```
Compound condition — `samples/transformations/HL7_test_multiple_files.ktr`:
```xml
<compare>
  <condition>
    <negated>N</negated>
    <conditions>
      <condition>
        <negated>N</negated>
        <leftvalue>Value</leftvalue>
        <function>IS NOT NULL</function>
        <rightvalue/>
      </condition>
      <condition>
        <negated>N</negated>
        <operator>AND</operator>        <!-- from the 2nd subcondition on: AND | OR | AND NOT | OR NOT | XOR -->
        <leftvalue>ParentGroup</leftvalue>
        <function>=</function>
        <rightvalue/>
        <value><name>constant</name><type>String</type><text>ADT_A01</text>
          <length>-1</length><precision>-1</precision><isnull>N</isnull><mask/></value>
      </condition>
    </conditions>
  </condition>
</compare>
```
`<function>`: `=`, `<>`, `<`, `<=`, `>`, `>=`, `REGEXP`, `IS NULL`, `IS NOT NULL`, `IN LIST`, `CONTAINS`,
`STARTS WITH`, `ENDS WITH`, `LIKE`, `TRUE`. (Spoon writes them escaped: `&#x3d;`, `&#x3c;&#x3e;`…)
**Pitfalls.** The targets must be **exact step names**, and the hop `FilterRows → target` must also exist
for each of them (in Spoon they show up as green/red hops). With both empty, only the *true* rows pass, to all
output hops. If you set only `<send_true_to>`, the false rows are discarded. The constant: the type in
`<value><type>` must be compatible with the field (comparing an Integer with `<type>String</type>` gives odd results);
for numbers use `<type>Integer</type>` / `Number`, for dates `Date` + `<mask>yyyy/MM/dd HH:mm:ss.SSS</mask>`.
`<` inside `<function>` must be written as `&lt;`.

### Switch / case — `SwitchCase`
Routes each row to a step according to the value of a field (several targets).
Example: `samples/transformations/Switch-Case - substring example.ktr`
```xml
<fieldname>text</fieldname>
<use_contains>Y</use_contains>          <!-- Y = "contains", N = equality -->
<case_value_type>String</case_value_type>
<case_value_format/>
<case_value_decimal/>
<case_value_group/>
<default_target_step>others</default_target_step>
<cases>
  <case><value>world</value><target_step>world</target_step></case>
  <case><value>hello</value><target_step>hello</target_step></case>
</cases>
```
**Pitfalls.** Each `<target_step>` and the `<default_target_step>` need their own hop from the Switch/case. Without a default,
rows that match no case are lost. Several values can go to the same target (one `<case>` per value).

### Append streams — `Append`
Concatenates two streams: first all the rows from *head*, then those from *tail*.
Example: `samples/transformations/XML Input Stream (StAX) Test 5 - Performance Test Data for Element Blocks.ktr`
```xml
<head_name>Append streams 2</head_name>
<tail_name>Select values 2</tail_name>
```
**Pitfalls.** Both streams must have **the same structure** (same fields, same order and types) and both
hops must exist. To merge more than two, or when order does not matter, it is enough to point several hops at the same step
(e.g. a `Dummy`): Kettle mixes the inputs (this also requires an identical structure).

### Dummy (do nothing) — `Dummy`
Does nothing: join point, end of a branch, or marker.
Example: `samples/transformations/Get File Names - Remove extension.ktr` — **empty** fragment (wrapper only).

### Abort — `Abort`
Aborts the transformation when rows reach it (validations).
Example: `samples/transformations/Rounding.ktr` + 9.4 defaults
```xml
<row_threshold>0</row_threshold>       <!-- abort when more than N rows are received -->
<message>Valor no esperado</message>
<always_log_rows>Y</always_log_rows>
<abort_option>ABORT_WITH_ERROR</abort_option>  <!-- ABORT | ABORT_WITH_ERROR | SAFE_STOP -->
```
**Pitfall.** `ABORT` (the default value) stops the transformation but does not add to the error count; for the job
to treat it as failed (and follow the error hop) use `ABORT_WITH_ERROR`. `<abort_option>` does not appear in the samples (they predate 9.x).

## Lookups and joins

### Stream lookup — `StreamLookup`
Enriches the main stream by looking values up in another stream loaded into memory (in-memory «lookup» join).
Example: `samples/transformations/Stream lookup - basics.ktr`
```xml
<from>Tab B</from>                      <!-- step that provides the lookup table (info stream) -->
<input_sorted>N</input_sorted>
<preserve_memory>N</preserve_memory>
<sorted_list>N</sorted_list>
<integer_pair>N</integer_pair>
<lookup>
  <key>
    <name>Mandt</name>                  <!-- field of the MAIN stream -->
    <field>B_Mandt</field>              <!-- field of the LOOKUP stream -->
  </key>
  <value>
    <name>B_Zusatz</name>               <!-- lookup field to bring in -->
    <rename>B_Zusatz</rename>           <!-- name in the output -->
    <default/>                          <!-- value when there is no match -->
    <type>String</type>
  </value>
</lookup>
```
**Pitfalls.** The lookup step is given in **`<from>`** (there is no `<lookup_step>`), and the hop
`Tab B → Stream lookup` is also required; the main stream is the other input hop. If there are several matches in the lookup
it keeps only one (it does not multiply rows). No match → fields get `<default>` or null (rows are not filtered: for an inner join,
filter by null afterwards). The whole lookup stream goes into memory.

### Database lookup — `DBLookup`
Looks up values in a DB table for each row (with optional cache).
Structure (defaults + API; there are no samples):
```xml
<connection>dwh</connection>
<cache>Y</cache>
<cache_load_all>N</cache_load_all>
<cache_size>5000</cache_size>
<lookup>
  <schema/>
  <table>dim_cliente</table>
  <orderby/>
  <fail_on_multiple>N</fail_on_multiple>
  <eat_row_on_failure>N</eat_row_on_failure>  <!-- Y = discards rows with no match (inner join) -->
  <key>
    <name>id_cliente</name>             <!-- stream field -->
    <field>cliente_id</field>           <!-- table column -->
    <condition>=</condition>            <!-- = | <> | < | <= | > | >= | LIKE | BETWEEN | IS NULL | IS NOT NULL -->
    <name2/>
  </key>
  <value>
    <name>sk_cliente</name>             <!-- column to return -->
    <rename>sk_cliente</rename>         <!-- name in the stream -->
    <default>-1</default>
    <type>Integer</type>
  </value>
</lookup>
```
**Pitfall.** Here `<name>`/`<field>` in `<key>` follow the same convention as InsertUpdate (stream / table), and in
`<value>`, `<name>` is the column. Without an index on the table, it is slow. The default text of `<table>` depends on the
locale («lookup table» / «tabla de búsqueda»): always overwrite it.

### Merge join — `MergeJoin`
Classic join (INNER, LEFT/RIGHT/FULL OUTER) between two **sorted** streams.
Example: `samples/transformations/Merge Join - Join 2 sorted data sets.ktr`
```xml
<join_type>FULL OUTER</join_type>       <!-- INNER | LEFT OUTER | RIGHT OUTER | FULL OUTER -->
<step1>Text file input</step1>          <!-- left stream -->
<step2>Text file input 2</step2>        <!-- right stream -->
<keys_1><key>pid</key></keys_1>
<keys_2><key>pid</key></keys_2>
```
**Pitfalls.** **Both inputs must be sorted by the keys** (same order, ascending) — without a preceding `SortRows`
it gives wrong results **with no error**. Hops from `step1` and `step2`. If both streams have fields with
the same name, the one from the right stream is renamed with the suffix `_1`. Keys are paired by position in `keys_1`/`keys_2`.

### Merge rows (diff) — `MergeRows`
Compares a reference stream with a new one and flags each row: `identical`, `changed`, `new`, `deleted`.
Example: `samples/transformations/Merge rows - mergs 2 streams of data and add a flag.ktr`
```xml
<keys><key>pid</key></keys>
<values><value>value</value></values>
<flag_field>flagfield</flag_field>
<reference>Text file input</reference>   <!-- "old" stream -->
<compare>Text file input 2</compare>     <!-- "new" stream -->
<compare>
</compare>
```
**Pitfalls.** Yes: there are **two** `<compare>` tags; the first one is the name of the step to compare, the second one (empty)
is a legacy condition block. Both inputs **sorted by the keys** and with the same structure.
It is usually followed by `SwitchCase` on `flagfield` or by `SynchronizeAfterMerge`.

### Join rows (cartesian product) — `JoinRows`
Cartesian product of all inputs, with an optional condition.
Example: `samples/transformations/Calculate median and percentiles using the group by steps.ktr`
```xml
<directory>%%java.io.tmpdir%%</directory>
<prefix>out</prefix>
<cache_size>500</cache_size>
<main>group</main>                      <!-- "main" step (read as a stream; the others are cached) -->
<compare>
  <condition>
    <negated>N</negated>
    <leftvalue/>
    <function>=</function>
    <rightvalue/>
  </condition>
</compare>
```
**Pitfalls.** Typical use: adding to each row a single aggregated value (total, maximum…) that comes from another
1-row branch. With large streams it blows up (N×M). An empty condition (as above) = no filter.

## Scripting and DB

### Modified Java Script Value — `ScriptValueMod`
JavaScript (Rhino) per row; widely used in the samples (55).
Example: `samples/transformations/XML Join - Create a multilayer XML file.ktr`
```xml
<compatible>N</compatible>
<optimizationLevel>9</optimizationLevel>
<jsScripts>
  <jsScript>
    <jsScript_type>0</jsScript_type>    <!-- 0 = transformation script (per row), 1 = start, 2 = end -->
    <jsScript_name>Script 1</jsScript_name>
    <jsScript_script>var nombre_completo = nombre + " " + apellido;
var es_mayor = edad &gt;= 18;</jsScript_script>
  </jsScript>
</jsScripts>
<fields>
  <field>
    <name>nombre_completo</name>        <!-- JS variable -->
    <rename>nombre_completo</rename>    <!-- output field -->
    <type>String</type>
    <length>-1</length>
    <precision>-1</precision>
    <replace>N</replace>                <!-- Y = overwrites the existing field with that name -->
  </field>
</fields>
```
**Pitfalls.** New variables are only output if they are listed in `<fields>`. `<compatible>Y</compatible>` is the old mode
(`campo.getString()`, as in the sample); with `N` the fields are plain JS values. A Kettle Integer arrives as a
JS number (double): for `<type>Integer</type>` it is truncated. Escape `<`, `&&` in the XML. Slow: prefer
Calculator/Formula/Janino when they are enough.

### Execute SQL script — `ExecSQL`
Runs SQL at initialization (DDL, truncates) or once per row.
Example: `samples/transformations/Table Output - Tablename in field.ktr`
```xml
<connection>SampleDataAdmin.H2</connection>
<execute_each_row>N</execute_each_row>
<single_statement>N</single_statement>
<replace_variables>Y</replace_variables>
<quoteString>N</quoteString>
<sql>CREATE TABLE IF NOT EXISTS ventas (id INT, total DECIMAL(10,2));
TRUNCATE TABLE ventas;</sql>
<set_params>N</set_params>
<insert_field/>
<update_field/>
<delete_field/>
<read_field/>
<arguments>
</arguments>
```
**Pitfalls.** With `<execute_each_row>N</execute_each_row>` the SQL runs **during the step's initialization**
(before any rows flow), but all steps initialize in parallel: there is no ordering between
several `ExecSQL` steps, nor relative to other steps that touch the DB in their init. For prior DDL, the clean approach is the
`SQL` job entry before the `TRANS` one. Multiple statements separated by `;`.
`<replace_variables>Y` to use `${VAR}`.

### Dimension lookup/update — `DimensionLookup`
Slowly changing dimension (SCD type 1/2): looks up/inserts/versions and returns the technical key.
Example: `samples/jobs/Slowly Changing Dimension/DimensionLookup - update dimension table 2.ktr`
```xml
<schema/>
<table>D_CUSTOMER</table>
<connection>SampleDataAdmin.H2</connection>
<commit>100</commit>
<update>Y</update>                      <!-- Y = lookup + update; N = lookup only -->
<fields>
  <key>
    <name>id</name>                     <!-- natural key in the stream -->
    <lookup>id</lookup>                 <!-- column in the dimension -->
  </key>
  <date>
    <name>updated</name>                <!-- date field from the stream (empty = system date) -->
    <from>date_from</from>
    <to>date_to</to>
  </date>
  <field>
    <name>Name</name>
    <lookup>Name</lookup>
    <update>Insert</update>             <!-- Insert = SCD2 (new version) | Update = SCD1 | Punch through | LastVersion... -->
  </field>
  <return>
    <name>customer_tk</name>            <!-- technical (surrogate) key -->
    <rename/>
    <creation_method>autoinc</creation_method>  <!-- autoinc | tablemax | sequence -->
    <use_autoinc>Y</use_autoinc>
    <version>version</version>
  </return>
</fields>
<sequence/>
<min_year>1900</min_year>
<max_year>2199</max_year>
<cache_size>5000</cache_size>
<preload_cache>N</preload_cache>
<use_start_date_alternative>N</use_start_date_alternative>
<start_date_alternative>none</start_date_alternative>
<start_date_field_name/>
<useBatch>N</useBatch>
```
**Pitfalls.** There are **two** `<update>` tags: the step-level one (mode) and the one in each `<field>` (change type). The table
needs the technical columns (`customer_tk`, `version`, `date_from`, `date_to`); Spoon creates them with the «SQL» button.
With `autoinc` the column must be auto-increment in the DB.

### Combination lookup/update — `CombinationLookup`
«Junk»/type 1 dimension keyed by a combination of keys: returns (or creates) the technical key.
Example: `samples/transformations/Combination Lookup - Create new ids.ktr`
```xml
<schema/>
<table>dim_territorio</table>
<connection>dwh</connection>
<commit>100</commit>
<cache_size>9999</cache_size>
<replace>N</replace>                    <!-- Y = remove the key fields from the stream -->
<preloadCache>N</preloadCache>
<crc>N</crc>
<crcfield>hashcode</crcfield>
<fields>
  <key><name>Territory</name><lookup>Territory</lookup></key>
  <return>
    <name>id</name>
    <creation_method>tablemax</creation_method>
    <use_autoinc>N</use_autoinc>
  </return>
</fields>
<sequence/>
<last_update_field/>
```
**Pitfall.** It does not version (there are no dates): a new combination → a new row. `tablemax` is not safe with
concurrent loads.

## Variables

### Set variables — `SetVariable`
Turns a field of the (single) row into a variable for the parent/root job or the JVM.
Example: `samples/jobs/process all tables/set variables.ktr` + 9.4 defaults
```xml
<fields>
  <field>
    <field_name>tablename</field_name>
    <variable_name>TABLENAME</variable_name>
    <variable_type>ROOT_JOB</variable_type>  <!-- JVM | PARENT_JOB | GP_JOB | ROOT_JOB -->
    <default_value/>
  </field>
</fields>
<use_formatting>Y</use_formatting>
```
**Pitfalls.** It must receive **exactly one row** (with more, it fails). The variable is **not** visible in the same
transformation that defines it (variables are resolved at startup): use it in the next transformation of the
job. `PARENT_JOB` is usually the right choice.

## Most used job entries (`.kjb`)

`<entry>` elements have a different wrapper: `<name>`, `<description>`, `<type>`, `<attributes/>`, the fragment, and at the end
`<parallel>N</parallel><draw>Y</draw><nr>0</nr><xloc>..</xloc><yloc>..</yloc><attributes_kjc/>`.

| Entry | `<type>` | Notes |
|---|---|---|
| Start | `SPECIAL` | `<start>Y</start><dummy>N</dummy>` + `<repeat>N</repeat><schedulerType>0</schedulerType>…`. There must be exactly one. |
| Dummy | `SPECIAL` | `<start>N</start><dummy>Y</dummy>` |
| Transformation | `TRANS` | `<specification_method>filename</specification_method><filename>${Internal.Entry.Current.Directory}/carga.ktr</filename>`… (see `job-entries/TRANS.xml`) |
| Job | `JOB` | `<specification_method>filename</specification_method><filename>…kjb</filename>` |
| Success | `SUCCESS` | empty fragment |
| Abort job | `ABORT` | `<message>` |
| SQL | `SQL` | `<sql>`, `<connection>`, `<useVariableSubstitution>` |
| Set variables | `SET_VARIABLES` | |
| Write to log | `WRITE_TO_LOG` | `<logmessage>`, `<loglevel>` |
| Check if file exists | `FILE_EXISTS` | `<filename>` |

Job hops (`<hops><hop>`): `<from>`, `<to>`, `<from_nr>0</from_nr>`, `<to_nr>0</to_nr>`, `<enabled>Y</enabled>`,
`<evaluation>Y</evaluation>` (Y = only on success, N = only on failure), `<unconditional>N</unconditional>` (Y = always;
the hop leaving START is unconditional). Full example: `samples/jobs/Slowly Changing Dimension/create - populate - update slowly changing dimension.kjb`.
